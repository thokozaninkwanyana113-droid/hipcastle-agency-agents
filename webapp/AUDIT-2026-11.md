# Hipcastle Agency — Program Audit (27 November 2026)

**Scope:**
- the live system at hipcastle.fly.dev and www.hipcastle.agency
- `main`, the version that is live
- the two unreleased features on the `integrations-suite` branch: the design studio and the delivery integrations

**Method:**
- the full automated test suite
- a dependency vulnerability scan
- a production build
- live probes of the site: health, security headers, access control, rate limits
- the new integrations called against the **real** public APIs (eTenders, PageSpeed, the site monitor)
- a security code review of authentication, payments, uploads, outbound requests, AI features and deployment

## Verdict

**The core platform is production-ready and well protected.** The main risks are operational, not code defects:
- payments are still in sandbox mode
- off-site backups are probably not configured (this can't be confirmed from outside)
- everything runs on one server

The audit found **three real defects, all in the new, unreleased integrations**. All three are fixed, tested and pushed.

| Area | Score | Summary |
|---|---|---|
| Functionality | **A−** | 111/111 automated tests pass across 11 suites. Every client journey is covered end to end: enquiry, order, agreement, payment, delivery, support, care plan and feedback. Two finished features are not live yet. |
| Stability | **B** | Healthy: 6.6 days without a restart, health checks, a graceful shutdown, automatic restart after a crash and crash alerts. It runs as a single machine with a SQLite database on a 1 GB volume. |
| Security | **A−** | Strong headers, tight payment verification, hashed reset tokens, rate limits, no secrets in the code and 0 vulnerable dependencies. There's no second login factor for admins, and logins last 7 days. |
| Integrations | **B−** | The code is solid and tested. Few integrations are switched on in production yet. Two of the public APIs behave worse in reality than their documentation says (fixed or documented). |

## 1. Functionality

- **Tests:** 111 passing, 0 failing, in 11 suites: API, pipeline, care plans, customer service, launch, operations, week-1 services, GEO/comms, Operator, design studio and integrations.
- **Build:** the client builds cleanly. Pages are split into separate files that each load on demand.
- **Codebase:** about 16,600 lines (server and client).
- **Live:** the health check is OK. Both domains serve the site. Admin and Operator APIs require a login (401 without one).
- **Not yet live:** the **design studio** and **delivery integrations** are on the `integrations-suite` branch and need a pull request, merge and deploy.
- **Live configuration:**
  - payments show **PayFast in test (sandbox) mode**
  - Ozow isn't configured
  - bot protection on forms (Cloudflare Turnstile) isn't set up
  - the Operator runs in rules mode unless `ANTHROPIC_API_KEY` is set

## 2. Stability

| Check | Result |
|---|---|
| Uptime | Up 6.6 days without a restart. The health check runs every 30 s. |
| Crash handling | Crashes are logged and alerted, and the process exits so Fly restarts it. Shutdown on deploy is graceful. |
| Background jobs | All run inside the app. Each job is protected from running twice at once. Every outbound request has a timeout. |
| Database | SQLite in WAL mode with a busy timeout. Upgrades are applied automatically at startup. |
| Backups | Daily snapshot with 7 kept **on the same volume**. Copying them to S3 storage only happens if `BACKUP_S3_*` is set. |
| Capacity | One `shared-cpu-1x` machine with 512 MB and a 1 GB volume in Johannesburg. That's fine for a small agency. |

**Risks**
- **S1 (high, operational): no proven off-site backup.** If the volume is lost, all clients, invoices and agreements go with it.
  - Set the `BACKUP_S3_*` secrets: Cloudflare R2 or AWS Cape Town (af-south-1).
  - Then confirm "Database backup" in Command Centre → System says *uploaded*.
- **S2 (medium): single point of failure.** One machine in one region; SQLite can't scale out. If a restart fails, the site is down.
  - Acceptable for now. Revisit when uptime is promised in contracts. At that point, move to Fly Postgres, or use LiteFS with a second machine.
- **S3 (medium): disk headroom.** Seven local snapshots plus design files stored in the database will fill 1 GB over time.
  - Extend the volume to 3 GB, about R15/month: `fly volumes extend <id> -s 3`.
- **S4 (low): slow report refreshes.** A manual PageSpeed refresh can take 30–60 s inside one web request, which is close to Fly's idle-connection limit.
  - Move to a background refresh if users see timeouts.

## 3. Security

**Strong**
- **Transport and headers:** HTTPS enforced, HSTS, a strict Content-Security-Policy (no inline scripts), and frame, referrer and MIME-sniffing protection. The new design file downloads add a sandboxing policy.
- **Authentication:**
  - passwords hashed with bcrypt
  - the app refuses to start in production without a JWT secret and admin password
  - every session can be revoked at once (token versioning)
  - reset tokens are hashed, expire in 1 hour and can be used once
  - "forgot password" doesn't reveal whether an account exists
- **Rate limits:** login (verified live: blocked after 20 attempts), sign-up, password reset, enquiries, newsletter, chat (AI cost) and checkout.
- **Payments:** PayFast ITNs are checked for signature, merchant ID, amount, PayFast source IP, and with PayFast's own server. Ozow is checked for hash, site code, amount, test-in-live and a status lookup. The test gateway can't run in production.
- **Data handling:**
  - all SQL is parameterised
  - inputs are validated (zod)
  - errors never reveal internals
  - passwords, card and ID numbers are removed from anything clients type
  - customer text sent to AI is treated as untrusted data, never as instructions
  - every outbound email and all ad spend need a person's approval
- **Dependencies:** `npm audit` found 0 vulnerabilities (server and client).

**Fixed during this audit**
- **F1 (medium): SSRF in website monitoring.** The server would fetch any address staff entered, including its own internal network.
  - It now refuses private, loopback, link-local and internal addresses (checked after DNS lookup).
  - It no longer follows redirects.
  - A test covers it.

**Open recommendations**
- **R1 (medium): two-factor sign-in for admin and staff.** One admin account controls payments, client data and settings. Add TOTP (authenticator app) for admin and staff.
- **R2 (medium): bot protection is off.** Turn on Cloudflare Turnstile by setting `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`; the forms already support it. This stops spam enquiries, sign-ups and chat abuse.
- **R3 (low): long logins stored in the browser.** Sessions last 7 days in browser storage. The strict CSP makes theft hard, but shorter staff sessions (e.g. 12 h) would reduce risk.
- **R4 (low): per-account lockout.** The login limit is per IP address, so a slow attack spread across many addresses isn't stopped. Add a short lockout after about 10 failures on one account.
- **R5 (low): container runs as root.** Run as the `node` user. This needs care, because the Fly volume is owned by root.
- **R6 (info): Microsoft 365 mailbox access.** `Mail.Read` covers every mailbox in your Microsoft 365 tenant unless an Exchange application access policy limits it to one. Apply the policy, as the setup steps say.
